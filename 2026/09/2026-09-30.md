#### User updates time out on large teams
- **Repo:** `api-users` · branch: `fix/add-user-to-schedules-timeout`
- **What was done:** Fixed a regression from PR #316. After a user was saved, the schedule step checked every schedule once for each team member. On a 2,100-person team this went past the database's 10-second limit. The password and profile changes had already been saved, but the user still got an error. Matching now uses `$setIsSubset` instead of `$all`, and the benchmark went from over 600 s to a fraction of that. I posted the root cause and fix on the Fizzy card.
- **Commits:**
  - `d17242bf` — fix(users): match team schedules with $setIsSubset, not $all, so large teams don't time out user updates
- **PR:** [#324 — fix(users): match team schedules with $setIsSubset, not $all, so large teams don't time out user updates](https://github.com/Nimbly-Technologies/api-users/pull/324)

#### Outbox retry budget
- **Repo:** `audit-lite` · branch: `master`
- **What was done:** `retryCount` was incremented on the retryable branch of `nextRowState` but was never compared to a limit, so outbox rows could retry forever. #### ANR triage: AUDIT-LITE-V2-E7
- **Repo:** `audit-lite`
- **Question:** What causes Sentry issue 6278074333 on the latest updates?
- **Outcome:** This is a generic Android ANR, and none of our code shows up as the cause.
